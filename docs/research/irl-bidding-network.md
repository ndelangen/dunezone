# IRL bidding browser and network capabilities

Checked on 9 November 2026 for [Bidding tool: establish browser and network capabilities](https://github.com/ndelangen/dunezone/issues/2837).

The chosen design can use direct data channels when they connect and a websocket relay when they do not. It cannot promise that devices on the same Wi-Fi connect directly, that a locked phone receives a timely turn alert, or that the current prototype restores a complete table after a reload. Those limits affect the specification, even if the transport choice stays unchanged.

This is documentation research and source inspection. No physical iPhone, iPad, Android device, guest network or interrupted internet connection was tested. Browser support below describes published capability, not a compatibility certification for this tool.

## Connectivity facts

The prototype supplies `iceServers: []`. It exchanges one offer and answer through the relay and sends application messages through an open data channel, otherwise through the relay. Its Storybook mode uses BroadcastChannel within one browser, so those stories do not exercise the deployed worker or real device networking. [Prototype transport](https://github.com/ndelangen/dunezone/blob/51bf76f09c07e849d8df3a0d0d9bb9677d92f50f/src/app/routes/_app/tools/bidding/tableLink.ts)

An empty server list supplies no STUN or TURN service. ICE can use host candidates without those services, but candidate reachability depends on routing, firewalls and browser policy. Host addresses include more than private Wi-Fi addresses, so the prototype comment that this restricts connections to the room is too strong. Inference: the lack of STUN and TURN is neither proof of proximity nor an access-control rule. [ICE candidate gathering](https://www.rfc-editor.org/rfc/rfc8445#section-5.1.1), [WebRTC IP address handling](https://www.rfc-editor.org/rfc/rfc8828#section-5)

WebRTC signaling is separate from the peer connection. In this design, new peers need the online relay to exchange their offer and answer. A working direct connection can carry application data without using that relay for each message, but a reload creates new connection state and needs signaling again. This is a consequence of the selected signaling design, not a general impossibility of offline browser communication. [WebRTC signaling guide](https://webrtc.org/getting-started/peer-connections#signaling), [prototype connection setup](https://github.com/ndelangen/dunezone/blob/51bf76f09c07e849d8df3a0d0d9bb9677d92f50f/src/app/routes/_app/tools/bidding/tableLink.ts#L337-L384)

The following are design expectations to verify, not completed test results:

| Situation                                                              | What the specification can rely on                                                                                                                                    |
| ---------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Devices on home Wi-Fi, both online                                     | Attempt a direct link. Keep relay bidding available when it does not connect.                                                                                         |
| Wi-Fi isolates devices but permits both outbound websocket connections | Use the application relay. Local peer connectivity is not required for that path.                                                                                     |
| Separate networks or a phone on cellular                               | Relay participation can work if each device can reach the service. Direct connectivity is not promised.                                                               |
| No internet before joining                                             | The current design cannot load an uncached page or perform initial relay signaling. Offline voice capability does not establish offline pairing.                      |
| Internet disappears after a direct link opens                          | Some direct traffic may continue, but the prototype does not establish an offline-continuity guarantee. Its relay-presence handling can tear down a live direct link. |
| Direct traffic and the relay both fail                                 | A phone has no path to the tablet. The spec must choose the table's response and explain unconfirmed actions.                                                         |

These rows follow the transport's routing and signaling paths. Network availability is a condition, not something the application can guarantee. [Prototype transport](https://github.com/ndelangen/dunezone/blob/51bf76f09c07e849d8df3a0d0d9bb9677d92f50f/src/app/routes/_app/tools/bidding/tableLink.ts#L229-L288)

## Mobile lifecycle and attention

Mobile pages may freeze or disappear while hidden. A frozen page cannot be expected to run its JavaScript timers, and discard may happen without a final event in which to save state. Chrome's lifecycle guidance recommends handling hidden state as a possible session end and reopening connections after resumption. The exact transition and timing vary by browser. The specification therefore needs resume and reconnect behavior rather than a promise of continuous background operation. [Chrome lifecycle guidance](https://developer.chrome.com/docs/web-platform/page-lifecycle-api)

Screen Wake Lock helps keep a visible page's screen awake. The API requires a fully active, visible document, may release a lock for power or operating-system reasons, and does not override the user manually turning off the screen. It does not wake a locked phone when a bid arrives. The application needs to notice release and request a new lock when appropriate after returning to the page. [Screen Wake Lock specification](https://www.w3.org/TR/screen-wake-lock/)

WebKit shipped screen wake lock in Safari 16.4 and added support for iOS and iPadOS Home Screen web apps in 18.4. This matters if the spec chooses to support an installed web app as well as an ordinary browser tab. These release notes establish availability, not uninterrupted operation under every power condition. [Safari 16.4](https://webkit.org/blog/13966/webkit-features-in-safari-16-4/), [Safari 18.4](https://webkit.org/blog/16574/webkit-features-in-safari-18-4/)

The browser compatibility dataset records `navigator.vibrate` support in Chrome for Android with a user-gesture requirement, and no support in Safari or iOS Safari. Treat vibration as optional feedback even where exposed. The vibration specification rejects hidden-page vibration and does not make it a general notification mechanism. [Pinned browser compatibility data](https://github.com/mdn/browser-compat-data/blob/918d2d721cc80c26c2eed7e64c6fa43da59322fd/api/Navigator.json), [Vibration specification](https://www.w3.org/TR/vibration/)

The prototype calls `navigator.vibrate` when a turn changes and gives the active phone a visual state. It does not request a screen wake lock or provide a mechanism to wake an iPhone. Product wording should describe an on-screen turn indication while the remote is visible. Claiming that a sleeping phone's screen lights up would exceed the implementation and platform evidence. [Prototype remote](https://github.com/ndelangen/dunezone/blob/51bf76f09c07e849d8df3a0d0d9bb9677d92f50f/src/app/routes/_app/tools/bidding/LinkedTable.tsx#L504-L524), [active phone rendering](https://github.com/ndelangen/dunezone/blob/51bf76f09c07e849d8df3a0d0d9bb9677d92f50f/src/app/routes/_app/tools/bidding/LinkedTable.tsx#L617-L677)

The spec should name the supported browser and OS range. Feature-detect data channels, vibration and wake lock, and keep essential bidding controls usable when optional capabilities are absent. The existing voice and tablet controls are useful alternatives when a player puts their phone away. This is a recommendation for the product decision, not an additional approved requirement.

## Storage and reloads

Browser storage is not a durable backup. WebKit uses best-effort storage by default, can evict site data, and may grant persistent mode based on browser policy. Private browsing uses ephemeral state. User deletion and unavailable storage must also be handled. Local restoration can be promised only conditionally, with an observable failure path. [WebKit storage policy](https://webkit.org/blog/14403/updates-to-storage-policy/), [WebKit private browsing policy](https://webkit.org/tracking-prevention/#private-browsing-mode)

The prototype persists an auction and its undo list through `useAuctionGame`, and a device ID through `deviceId`. Storage failures are caught without telling the user that reload recovery is unavailable. The saved auction has only a version check, not full structural validation. [Auction persistence](https://github.com/ndelangen/dunezone/blob/51bf76f09c07e849d8df3a0d0d9bb9677d92f50f/src/app/routes/_app/tools/bidding/useAuctionGame.ts#L11-L54), [device identity](https://github.com/ndelangen/dunezone/blob/51bf76f09c07e849d8df3a0d0d9bb9677d92f50f/src/app/routes/_app/tools/bidding/tableLink.ts#L24-L38)

`LinkedTablet` generates a new table code unless its caller supplies one. Setup, seat holders and acknowledgements live in memory; the auction persistence hook mounts only after entering bidding. The remote's chosen faction and pending command also live in memory. Consequently, an unchanged device ID or a saved auction is not proof that the same connected table, ownership and outstanding actions survive reload. A recovery contract must cover those pieces together. [Tablet initialization](https://github.com/ndelangen/dunezone/blob/51bf76f09c07e849d8df3a0d0d9bb9677d92f50f/src/app/routes/_app/tools/bidding/LinkedTable.tsx#L162-L188), [bidding mount](https://github.com/ndelangen/dunezone/blob/51bf76f09c07e849d8df3a0d0d9bb9677d92f50f/src/app/routes/_app/tools/bidding/LinkedTable.tsx#L243-L254), [remote initialization](https://github.com/ndelangen/dunezone/blob/51bf76f09c07e849d8df3a0d0d9bb9677d92f50f/src/app/routes/_app/tools/bidding/LinkedTable.tsx#L492-L502)

## Protocol gaps that affect decisions

These are observations from the recorded prototype, not claims about released code:

- ICE gathering stops waiting after 1.5 seconds even if it is not complete. There is no trickle exchange for candidates found afterward. A missing candidate or stalled attempt needs an explicit timeout and retry policy; a five-second retry after a failed peer does not cover every negotiation that never reaches failure. [Gathering and connection lifecycle](https://github.com/ndelangen/dunezone/blob/51bf76f09c07e849d8df3a0d0d9bb9677d92f50f/src/app/routes/_app/tools/bidding/tableLink.ts#L177-L195), [retry path](https://github.com/ndelangen/dunezone/blob/51bf76f09c07e849d8df3a0d0d9bb9677d92f50f/src/app/routes/_app/tools/bidding/tableLink.ts#L315-L360)
- Relay presence controls the tablet's peer list. When it no longer lists a phone, the tablet drops that phone's direct connection. Inference: if the phone loses internet but still has local connectivity, the current presence rule can end the local connection too. Offline continuity requires a deliberate relationship between relay presence, direct reachability and table membership. [Presence processing](https://github.com/ndelangen/dunezone/blob/51bf76f09c07e849d8df3a0d0d9bb9677d92f50f/src/app/routes/_app/tools/bidding/tableLink.ts#L263-L274)
- The tablet acknowledges a command ID before checking its seat or whether the action applies. The remote treats that acknowledgement as completion. It cannot tell the player whether a bid was accepted, refused or merely received. Command IDs are held in memory, and commands do not carry an auction or turn revision. A delayed pass or raise can therefore reach a later turn for the same faction. The spec needs explicit action results, stale-action rejection and duplicate handling across the two transport paths. [Acknowledgements](https://github.com/ndelangen/dunezone/blob/51bf76f09c07e849d8df3a0d0d9bb9677d92f50f/src/app/routes/_app/tools/bidding/LinkedTable.tsx#L195-L210), [resends](https://github.com/ndelangen/dunezone/blob/51bf76f09c07e849d8df3a0d0d9bb9677d92f50f/src/app/routes/_app/tools/bidding/LinkedTable.tsx#L504-L554), [current-turn check](https://github.com/ndelangen/dunezone/blob/51bf76f09c07e849d8df3a0d0d9bb9677d92f50f/src/app/routes/_app/tools/bidding/SoundRemotes.tsx#L52-L77)
- The phone shows loss after five seconds without a state message, while the tablet broadcasts every two seconds. These are foreground heuristics. They do not prove that a command failed, and mobile suspension can delay both the heartbeat and the check itself. [State broadcast](https://github.com/ndelangen/dunezone/blob/51bf76f09c07e849d8df3a0d0d9bb9677d92f50f/src/app/routes/_app/tools/bidding/LinkedTable.tsx#L234-L241), [loss detection](https://github.com/ndelangen/dunezone/blob/51bf76f09c07e849d8df3a0d0d9bb9677d92f50f/src/app/routes/_app/tools/bidding/LinkedTable.tsx#L537-L554)

These findings belong in [Bidding tool: decide table authority, access and recovery](https://github.com/ndelangen/dunezone/issues/2836) and, for action ordering and correction, [Bidding tool: agree mixed-input behavior](https://github.com/ndelangen/dunezone/issues/2840). They do not require changing the agreed no-Convex, direct-plus-relay direction.

## Required physical checks

Record the device, OS and browser version, normal or private tab, network topology and observed transport for every run. Use at least one physical iPhone Safari, iPad Safari and Android Chrome remote, with a phone as central display as well as an iPad. The following checks remain unperformed:

| Check                                                                                               | Evidence to retain                                                                                                                          |
| --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Home Wi-Fi with all devices online, then a network with client isolation                            | Which transport each phone actually uses; successful bids over both direct and relay paths; no lost or repeated action when a path changes. |
| Internet loss on one remote, then on the tablet, then on the whole router while local Wi-Fi remains | Whether existing direct traffic survives; what happens to relay presence; clear action status and the agreed table behavior.                |
| Join before internet loss, join afterward, and reload during the outage                             | Distinct results for an existing connection, new signaling and cached-page availability.                                                    |
| Lock a remote, switch apps, leave it backgrounded, then return; repeat for the tablet               | Resynchronization, pending-action handling and the chosen timer policy. Confirm that an old action cannot affect a new turn.                |
| Reload the tablet and a remote after an accepted bid and while an acknowledgement is missing        | Same table and ownership if promised, exact count and auction state, no duplicated win or lost correction.                                  |
| Normal and private tabs, denied or cleared storage, low-power mode, explicit screen lock            | Honest restoration status; wake-lock release and reacquisition; no requirement for vibration or waking a locked screen.                     |

The product decisions must specify expected outcomes before these become pass/fail tests. In particular, choose whether a hidden or disconnected tablet pauses the timer, which recovery losses are acceptable, and whether continuing after internet loss is required or merely possible. Those are user decisions, not conclusions that the browser documentation can supply.
